# 🔬 Research Paper Answer Bot — Comprehensive System Architecture & Deep Dive Guide

Welcome to the full documentation for **Research Paper Answer Bot**, a production-grade, enterprise-ready Retrieval-Augmented Generation (RAG) system built over Generative AI and LLM research papers.

This guide provides an end-to-end breakdown of what was built, how every component works under the hood, a complete file-by-file inventory, architectural design decisions, and an evaluation of how this system matches state-of-the-art (SOTA) industry standards.

---

## 📌 Executive Summary

### What Was Built?
A full-stack RAG web application that allows users to:
1. **Ingest Research PDFs**: Extract, clean, and chunk multi-page academic papers (e.g., Attention Is All You Need, LLaMA, LoRA).
2. **Multi-Strategy Chunking & Dual Embeddings**: Generate vector embeddings using both cloud SOTA API models (`nvidia/nv-embedqa-e5-v5`, 1024-dim) and local comparison models (`BAAI/bge-m3`).
3. **Advanced Hybrid Retrieval Pipeline**: Perform dense semantic vector search (Cosine similarity via `pgvector`), full-text keyword search (`tsvector` / `tsquery`), and combine them using **Reciprocal Rank Fusion (RRF)** followed by **Cross-Encoder Reranking** (`ms-marco-MiniLM-L-6-v2`).
4. **Context-Aware Conversational Generation**: Stream answers generated by NVIDIA NIM (`meta/llama-4-maverick-17b-128e-instruct` or fallback LLMs) backed by conversation history and source citations with exact page numbers and relevance scores.
5. **Interactive Frontend Developer Benchmarking Panel**: Real-time evaluation dashboard embedded in the React UI allowing developers to switch retrieval strategies live and inspect latency, retrieved chunks, and fusion ranks.

## 📁 File-by-File Breakdown & Codebase Map

### 📦 Backend (`/backend`)

#### 1. Core & Configuration
- **`app/core/config.py`**
  - **Purpose**: Centralized application settings using `pydantic-settings`. Reads environment variables from `.env` with validation and default fallbacks (database URL, API keys, CORS origins, model names, chunking parameters).
  - **Why**: Keeps all environment configuration strongly typed and validated before application boot.

- **`app/core/db.py`**
  - **Purpose**: Sets up the async SQLAlchemy engine (`asyncpg`) and session factory (`AsyncSessionLocal`) connected to Neon PostgreSQL. Includes `clean_db_url()` to normalize connection strings and configure SSL.
  - **Why**: `asyncpg` provides high-performance non-blocking I/O essential for serving concurrent web requests while executing database vector queries.

- **`app/__init__.py`**
  - **Purpose**: Top-level package initialization. Implements a safe PyTorch DLL import fallback to handle environments with Windows Application Control restrictions without crashing the API server.

- **`app/main.py`**
  - **Purpose**: The FastAPI application entry point. Registers CORS middleware, mounts API routers (`health`, `papers`, `chat`), sets OpenAPI docs (`/docs`), and configures OS event loop policies.
  - **Why**: Decoupled, modular entry point following standard FastAPI production blueprints.

---

#### 2. Database ORM Models (`app/models/`)
- **`app/models/paper.py`**
  - **Purpose**: SQLAlchemy ORM model for academic papers (`papers` table). Stores title, authors, abstract, arXiv ID, PDF file path, ingestion status, and metadata.

- **`app/models/chunk.py`**
  - **Purpose**: Represents document chunks (`chunks` table). Features a 1024-dimensional `vector` column powered by `pgvector`, a PostgreSQL `tsvector` column for full-text search, page numbers, and chunk indices.
  - **Why**: Enables dual-index querying (HNSW vector index + GIN full-text index) directly within a single relational table.

- **`app/models/conversation.py`**
  - **Purpose**: Stores multi-turn chat sessions (`conversations` and `messages` tables) with role (`user`/`assistant`), token counts, latency metrics, and citation metadata.

---

#### 3. Ingestion Engine (`app/ingestion/`)
- **`app/ingestion/loaders.py`**
  - **Purpose**: PDF processing using `pypdf` and `pdfplumber`. Extracts text page-by-page while preserving page boundaries and metadata.

- **`app/ingestion/chunking.py`**
  - **Purpose**: Implements three distinct chunking algorithms:
    1. `fixed_512`: Fixed window of 512 tokens with 50-token overlap.
    2. `recursive`: LangChain `RecursiveCharacterTextSplitter` respecting paragraphs and sentence boundaries.
    3. `semantic`: Groups sentences based on cosine similarity transitions using sentence embeddings.
  - **Why**: Meets research standards by allowing quantitative comparison of chunking strategies on retrieval precision.

- **`app/ingestion/embedder.py`**
  - **Purpose**: Generates vector representations using `nvidia/nv-embedqa-e5-v5` (via NVIDIA NIM API) and `BAAI/bge-m3` (local `sentence-transformers`). Normalizes vector dimensions and batches API requests.

---

#### 4. Retrieval & Reranking Pipeline (`app/retrieval/`)
- **`app/retrieval/dense.py`**
  - **Purpose**: Performs pure dense vector retrieval using Cosine distance (`<=>` operator in `pgvector`) over HNSW indexes.

- **`app/retrieval/hybrid.py`**
  - **Purpose**: Combines dense vector search with sparse full-text keyword search (`ts_rank_cd`). Uses **Reciprocal Rank Fusion (RRF)**:
    $$\text{RRF\_Score}(d) = \sum_{m \in M} \frac{1}{k + r_m(d)}$$
  - **Why**: Solves the vocabulary mismatch problem (keyword search catches exact acronyms/model names; vector search catches semantic meaning).

- **`app/retrieval/reranker.py`**
  - **Purpose**: Applies a cross-encoder model (`cross-encoder/ms-marco-MiniLM-L-6-v2`) to re-score and re-rank the top-N candidates returned by RRF.
  - **Why**: Bi-encoders (vector embeddings) compute query and document representations independently. A Cross-Encoder processes query + document together through self-attention layers, boosting Precision@K significantly.

- **`app/retrieval/evaluator.py`**
  - **Purpose**: Automated retrieval evaluation script measuring Mean Reciprocal Rank (MRR@K), Hit Rate@K, and Normalized Discounted Cumulative Gain (NDCG@K) across different strategy configurations.

---

#### 5. RAG Chain & Memory (`app/rag/`)
- **`app/rag/chain.py`**
  - **Purpose**: Implements the RAG generation pipeline using LangChain Expression Language (LCEL). Formats context snippets with paper titles and page numbers, constructs system prompts, and handles streaming output from NVIDIA NIM LLM.

- **`app/rag/memory.py`**
  - **Purpose**: Manages multi-turn conversation memory, fetching previous context windows while enforcing maximum token limits to prevent context bloat.

---

#### 6. API Routes & Endpoints (`app/api/routes/`)
- **`app/api/routes/health.py`**: Liveness and readiness endpoints (`GET /health`).
- **`app/api/routes/papers.py`**: PDF upload (`POST /papers/upload`), list papers (`GET /papers`), and paper deletion (`DELETE /papers/{id}`).
- **`app/api/routes/chat.py`**: Chat endpoint (`POST /chat`) supporting streaming responses, strategy selection (`dense`, `hybrid`, `hybrid_rerank`), and returning citation metadata.

---

#### 7. Evaluation & Scripts
- **`backend/app/evaluation/ragas_eval.py`**: Automated RAGAS evaluation runner measuring Faithfulness, Answer Relevance, Context Precision, and Context Recall.
- **`backend/scripts/seed_db.py`**: Automated seed script downloading landmark GenAI papers from arXiv (Attention, LLaMA, LoRA, RAG) and ingesting them into Neon DB.
- **`backend/scripts/verify_seed.py`**: Database integrity check verifying chunk counts and vector embeddings.

---

### 🎨 Frontend (`/frontend`)

- **`src/api/client.ts`**: Axios/fetch HTTP client communicating with backend endpoints (`/chat`, `/papers`, `/health`).
- **`src/hooks/useChatSession.ts`**: Custom React hook managing active conversation state, message history, streaming tokens, and selected retrieval strategy.
- **`src/components/ChatWindow.tsx`**: Main chat interface container holding message list and input bar.
- **`src/components/MessageBubble.tsx`**: Renders user and AI responses with Markdown formatting and code syntax highlighting.
- **`src/components/SourceCitations.tsx`**: Expandable citation drawer displaying source paper titles, page numbers, and relevance scores.
- **`src/components/DevPanel.tsx`**: Live developer benchmark panel allowing real-time switching between retrieval modes (`dense`, `hybrid`, `hybrid_rerank`) and displaying retrieval latency and chunk scores.
- **`src/components/PaperLibrary.tsx` & `PaperUploader.tsx`**: Drawer for viewing ingested papers, chunk counts, and drag-and-drop uploading of new PDFs.

## 🛠️ Architectural Decisions & Technical Rationale

| Feature / Decision | Choice Made | Why This Choice? (Technical Rationale) |
|---|---|---|
| **Database & Vector Store** | **Neon PostgreSQL + `pgvector`** | Avoids data fragmentation caused by separate vector databases (e.g., Pinecone/Weaviate). Keeping vectors, relational paper metadata, and chat history in PostgreSQL guarantees ACID compliance and transactional consistency. |
| **Retrieval Strategy** | **Hybrid Search + RRF + Cross-Encoder Reranking** | Vector-only search fails on exact keyword/acronym matches (e.g., "LoRA rank r=8"). Hybrid search combines keyword BM25/tsvector + Dense vector search via Reciprocal Rank Fusion (RRF), while Cross-Encoder reranking ensures top-3 precision. |
| **Embedding Model** | **NVIDIA `nv-embedqa-e5-v5` (1024-dim)** | Rated #1 on MTEB (Massive Text Embedding Benchmark) for retrieval tasks. High dimensional density ensures nuanced representation of technical equations and paper terminology. |
| **LLM Provider** | **NVIDIA NIM (`meta/llama-4-maverick-17b-128e-instruct`)** | Enterprise-grade, ultra-low latency inference microservice with 128k context window support for complex research paper reasoning. |
| **Backend Framework** | **FastAPI + AsyncSQLAlchemy (`asyncpg`)** | Non-blocking asynchronous I/O handles concurrent streaming LLM responses without thread exhaustion. |
| **Frontend Framework** | **React + Vite + TypeScript + Tailwind CSS** | Provides sub-millisecond hot-reloading, type safety for complex API payloads, and clean responsive design. |
